# Skill：知识归纳与知识库维护（Knowledge Curation）

> **使用场景**：用户说“把这次学习整理进知识库”“补充某章”“归纳之前的 Linux 内容”“合并已有笔记”“为复习做一篇速览”“整理 Markdown 并交给 Codex”等。
>
> **可迁移性要求**：本文件是**普通 Markdown 操作规程**。不要依赖某一 AI 厂商、某一次聊天会话或某一个设备路径。只要 Agent 能读取仓库、接收来源材料、修改文件，就可以执行；不能直接修改文件时，交付待导入的 Markdown 和具体变更指引。

## 0. 为什么有这条流程

本仓库源于一个实际问题：用户持续借助 AI 学习嵌入式 Linux、C/C++、单片机与 DSP、信号处理/仿真等技术主题。长对话方便追问，却不适合按章节检索和长期复习。

因此采用统一的知识沉淀模式：

```text
用户学习/提问/实验
      ↓
用户显式提供本次相关材料
      ↓
Agent 梳理“哪些是事实、结论、推测、过程和仍有疑问”
      ↓
查找 docs/ 中对应知识：修改已有？合并？新增？
      ↓
生成或修订可独立阅读的 Markdown 教程
      ↓
更新课程导航、站内链接、图片与必要元数据
      ↓
检查差异、运行构建、用户复核
      ↓
Git 版本管理与可选远程同步
```

**目标**：提高知识的正确性、可追溯性、可查找性和复习效率。

**非目标**：逐字聊天存档、未经审查的 AI 百科自动生成、默认自动抓取历史聊天、替用户宣布已完成学习、默认公开部署。

## 1. 输入约定：没有材料就不能假装知道

可能收到的来源材料包括：

- 用户粘贴的当次讨论、总结、问题及更正意见；
- `inbox/` 下的 Markdown 草稿；
- 用户提供的 `.md`、PDF、Word、代码、截图、阶段报告；
- 当前仓库已存在的 `docs/` 页面；
- 用户明确授权查阅的外部资料或工具输出。

**先看清本次到底提供了什么**。本仓库虽然保留了已归档文档，但不包含所有历史 AI 对话；新 Agent 不得把“用户过去肯定学过”当作证据。

如果来源材料不足：

1. 能从**现有仓库文档**确认的内容，可在注明范围后整理；
2. 缺少关键数据、结论或原始内容时，请求用户提供，或者只交付明确标注不完整的草稿；
3. 若用户要求基于现有材料先做最佳努力，仍须列出缺失部分；
4. 不得为了填满教程模板编造具体案例、实验参数、测试结果或引用。

### 区分四种信息

| 类型 | 处理方式 |
| --- | --- |
| A. 来源直接支持、已经形成的结论 | 准确保留条件、术语、数值和结论 |
| B. 来源中的过程性提问、失败尝试 | 提炼成“常见问题/易错点”；仅在对理解有帮助时保留 |
| C. 尚未确认的假设、争论、计划 | 标注“待验证/待讨论/计划”，不可写成确定事实 |
| D. Agent 补充的外部知识或推断 | 仅在用户授权或任务确实需要时增加，显式区分于原材料；重要新增事实应能核查 |

**特别注意技术内容**：演示代码不等于已运行程序；理论推导不等于仿真验证；系统架构概览不等于用户已经完成驱动开发；定性猜想不等于实测结论。

## 2. 启动检查：认识仓库，而不是照抄目录模板

先做以下检查（只运行环境实际支持的命令）：

1. 阅读 `README.md`、根 `AGENTS.md` 和本文件。
2. 检查 `git status`，记录尚未提交的改动；不清除它们。
3. 检查 `package.json`、实际 VitePress 配置路径及 `docs/` 下课程目录。
4. 搜索同义标题、关键词、相关现有页面，以及课程首页和导航入口。
5. 找到当前任务对应的材料，核对是否能完整读取。
6. 根据当前仓库选择目标文件，**不要假设**示例名称 `linux/03-poll-epoll.md` 一定存在。

若工程和源文件不可读，不要谎称已经“导入/构建完成”；应交付可复制的正文和明确的待执行步骤。

## 3. 判定本次任务类型

| 类型 | 典型输入 | 优先策略 |
| --- | --- | --- |
| **新课归档** | “今天学习了 `fork`，帮我记录” | 查重；补充现有进程章，缺失时新建 |
| **纠错与增补** | “之前的 `lseek` 解释不完整” | 定位原段，小范围修订，保留有效内容 |
| **批量历史迁移** | “把之前 Linux 学习整体导入” | 先设计主题映射，分批归档与去重 |
| **知识全景/速览** | “简要总结整个嵌入式 Linux，包括驱动” | 保持概览深度；以链接指向深入教程 |
| **课程结构整理** | “重新规划章节目录” | 不随意重写正文；先评估旧链接和影响范围 |
| **复习资料** | “提炼本章回顾和自测” | 优先在已有文章维护小结与自测，必要时另建索引 |

### 决策规则：新增、合并还是只修订？

1. **同一问题已有完整页面** → 增量修订原页面。
2. **主题相近、但材料补充了前置概念或新条件** → 合并到既有页面的合适小节。
3. **新内容确有独立学习目标，并且篇幅足以独立阅读** → 新建章节，并链接前后主题。
4. **内容覆盖多个主题但只要求快速回顾** → 建立/更新概览页，正文保持简洁，详细内容指向现有章节。
5. **无法判断两条结论是否冲突** → 暂不擅自统一，标出冲突和依据，留给用户审核。
6. **不需要改动** → 明确报告已覆盖，无需为“完成任务”制造额外文件。

在批量迁移或多文件修改前，先报告“目标章节 → 操作方式 → 依据 → 是否需用户确认”的简短映射。

## 4. 内容提炼规则

从材料中优先抽取：

- 本节解决的问题与学习目标；
- 核心概念及其边界、前提和适用条件；
- 必要的工作流程、调用关系、公式和图示；
- 有解释价值的示例代码、命令、编译与运行步骤；
- 用户曾追问的典型困难及最终得到的解释；
- 与其他章节的关系、常见误区及简要复习结论；
- 尚未解决的问题和后续可扩展方向（只在来源支持时保留）。

压缩讨论记录时，优先保留**纠正后结论**。如果旧观点的错误原因具有教学价值，可以作为“易错点”简短说明；不要把多轮探索原样复制。

**不要随意“补全”历史。** 举例：来源表明用户学习了 `select`、`poll`、`epoll`，进程部分已经开始；驱动曾跳过深入学习、后续只补过整体认识。知识库可解释驱动的全貌，但不能因此写“用户已完成驱动开发实战”。

## 5. 建议的文章结构（按实际主题灵活裁剪）

每篇文章应能脱离原始聊天直接阅读。可使用以下模板，但**不要保留无内容的占位小节**：

```markdown
---
title: Linux 进程基础
description: 进程概念、fork/exec、退出与回收
status: draft
tags: [Linux, 进程]
---

# Linux 进程基础

## 本节定位与学习目标

## 前置知识

## 核心概念

## 工作原理

## 代码或操作示例

## 常见问题与易错点

## 小结：快速复习

## 自测问题

## 相关章节与资料
```

- `status: draft` 表示初稿；`reviewed` 表示人工审阅；`verified` 只可用于明确存在符合项目要求的验证依据，不得由 AI 擅自提升。
- 需要快速认识一个系统时，应优先采用“整体架构 → 各模块的职责 → 工作链路 → 与后续章节关系 → 一页回顾”的简洁结构。
- 需要深入解释 API 或算法时，可增补参数表、错误码、边界场景、性能注意事项、验证步骤。
- 术语首次出现时可用“中文名（英文名，缩写）”，后续统一用词；保留 C/C++ 类型、函数名和精确符号。
- 代码块注明语言；可执行命令注明操作系统、依赖、用途和可能产生的副作用。
- 图片使用持久仓库资源；公式检查符号、单位、上下文是否一致。
- 所有引用必须真实存在。来源不足时写“待补参考资料”，不要创建虚构论文或链接。
- 如仓库已有更成熟的 frontmatter、文件命名和文章结构，优先沿用**现有项目约定**，而非强制使用本模板。

## 6. 修改仓库的安全步骤

### 步骤 A：输入和计划

输出一段简短计划，包括：来源文件、相关已有页面、候选操作（新增/修订/合并）、可能的导航修改以及待确认点。小修改可以直接执行，但不得盲目覆盖。

### 步骤 B：执行文档修改

- 只改当前任务涉及的页面，尽量最小差异。
- 发现重复主题时先合并，再用内部链接连接关联知识。
- 文章不要依赖“上次我们提到”“根据刚才的聊天”等上下文。
- 不删原始 `inbox/` 资料，除非用户明确批准；不要默认将它加入 Git。
- 不覆盖用户未提交的独立修改；发现冲突时说明位置并保留现场。
- 处理敏感科研、个人或工程资料时，先确认是否允许进入可能公开的站点。

### 步骤 C：维护 VitePress 展示

检查项目实际使用的目录和配置（可能是 `docs/.vitepress/config.mts`，也可能不同），按需：

- 在课程主页增加或调整章节入口；
- 在 `sidebar` 等导航配置中加入实际存在的新章节；
- 检查文章的相对链接、锚点、图片路径以及重命名影响；
- 遵守现有目录顺序，不把旧文章无理由整体重编号；
- 确保概览文章与深入文章互相链接，避免重复粘贴全文。

### 步骤 D：测试与核对

在具备终端权限时，按当前项目实际命令执行：

```bash
npm run docs:build
git diff --check
git status
```

再检查 `git diff`、文章标题层级、代码围栏、链接、图片和导航。若是代码任务，能在相符环境中执行则报告具体编译/运行命令；否则明确“示例未实际运行，仅检查文本/语法”。

如果构建失败，先判断是**本次改动造成**还是**仓库原有问题**；在授权范围内修复并报告。若环境不支持构建，不要写“构建通过”。

### 步骤 E：交付与人工审阅

按下面的固定结构报告（无内容的项可省略）：

```text
归档结果
- 输入依据：……
- 目标章节与处理方式：新增 / 修订 / 合并 / 无需修改
- 新增文件：……
- 修改文件：……
- 保留不动：……（如已覆盖同主题）
- 技术或来源待核查：……
- 验证：执行的命令 + 真实结果 / 未执行原因
- Git：是否提交 / 是否 push / 是否部署
- 建议人工复核：……
```

**默认不 push、不部署、不执行破坏性 Git 操作。** 是否创建本地 commit，以用户当前指令为准。

## 7. 三种常用任务的示范指令

### 7.1 新内容归档

> 请先阅读仓库 `AGENTS.md` 和 `skills/knowledge-curation/SKILL.md`。我提供了一份关于「主题」的 Markdown 草稿，请你根据其中内容整理知识，先检索相关章节，优先增量更新而不是重复建新文件；维护 VitePress 导航及内部链接，运行构建，并汇报未核查事项。不要 push 或发布。

### 7.2 补充纠错

> 我提供了对「某知识点」的更准确解释。请检索原章节，保留原有正确内容，仅修改受影响段落；如不同章节存在相互矛盾的说法，列出差异和处理依据。完成后给出 diff 摘要及构建结果。

### 7.3 批量迁移与知识概览

> 将我提供的「课程学习材料」整理进现有知识库。先扫描目录并做主题映射，划分“已经覆盖”“需要合并”“确实缺失”。对概览部分保持简洁，深度内容分章节；不能把教材知识覆盖当成我的实际学习进度。分批完成修改、链接检查和构建，不要自动上传远端。

## 8. 跨设备、跨 Agent 的交接约定

- **仓库保存**：本文件、`README.md`、`AGENTS.md`、`docs/`、站点配置、依赖锁文件和 Git 历史。
- **按需另行提供**：未归档聊天材料、教材、实验数据、个人进度更正、私有信息及当前任务要求。
- **新 Agent 的第一步**：阅读三份约定，检查真实仓库与 Git 状态，再以当前文件为准。
- **工具不兼容时**：不要伪称已编辑本地仓库；提供可直接复制的 Markdown、目标文件路径建议和未完成检查。
- **规则演进**：若用户决定调整目录或归档规范，应同步修订本文件与 `AGENTS.md` 中相关入口，避免多个矛盾版本。

## 9. 最终验收清单

- [ ] 来源材料可追溯；没有凭空补写“用户已经学过”或“实验已经完成”。
- [ ] 同主题资料没有不必要重复，改动前保留了旧章有效知识。
- [ ] 文章完整、独立可读、深度符合用户本次目标。
- [ ] 结论、条件、数值、示例运行状态准确或已注明待核查。
- [ ] 导航、课程首页、链接、图片和公式正确。
- [ ] 无不应公开的资料泄露或默认远端推送。
- [ ] 项目提供构建命令时已真实尝试，结果如实报告。
- [ ] Git diff 已检查，用户能明确知道修改了什么。

**核心原则：以材料为依据，以 Markdown 为长期资产，以增量维护为常态，以人工复核与可回滚版本为保障。**
